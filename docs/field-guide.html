Engineering field guide

How the pipeline framework actually runs

A guided walkthrough of the codebase for someone who wants to drive it, not just read about it: what each flow does from the moment it starts, which checks stand guard along the way, and the trade-offs behind decisions that aren't obvious just from reading the code.

3 process types· 5 modules· BigQuery-only config & storage· Java 17 / Apache Beam
01 — Foundations

Architecture at a glance

Five modules, one direction of dependency, one wire type. Almost every confusing question about "why is this class here and not there" traces back to this shape.

beam-core
Contracts only. Options, enums, SPI interfaces, model classes. Zero deps on siblings.
beam-io
Source/sink connectors, BQ config repos, checkpoint adapters. → core only.
beam-utils
Stateless helpers: schema fetch, GCS, secrets, calendars, token resolution. → core only.
beam-transforms
Pluggable BeamTransform SPI impls + per-source transforms. → core, utils.
beam-runner
Entry point & orchestration factories. → everything else.
beam-orchestrator (standalone Airflow-fanout JAR) depends on none of the above — a deliberate island, see the trade-off below.

The rule that matters most

beam-io never imports from beam-utils or beam-transforms. That's not an aesthetic preference — SmtpReportEmailAdapter lives in beam-runner instead of beam-io for exactly this reason: it needs SecretManagerUtils (beam-utils) and angus-mail (beam-transforms), and beam-io isn't allowed to reach for either. If you ever need an I/O adapter that wants a utils-only helper, that's the signal it belongs in beam-runner, not beam-io.

One wire type, everywhere

Every Beam transform passes PCollection<Row> with an explicit Schema via .setRowSchema(). No raw bytes, no bare Strings, no Avro-specific types leaking into transform boundaries. This is what lets SourceTransformChainAssembler chain LOOKUP → GROUP_BY → SORT_BY without any transform needing to know what came before it.

Trade-off — no JDBC, anywhere

All configuration and all data live in BigQuery. There is no relational database adapter in this framework at all (an earlier JDBC db/ package was fully removed). That buys one system to secure, scale, and back up — but it also means the framework inherits BigQuery's specific quirks as architectural constraints, not incidental ones. The clearest example: rows written via streaming insert are immediately visible to SELECT but can sit in BigQuery's internal streaming buffer for a while, during which DELETE/UPDATE/MERGE simply refuse to touch them. PostDownloadFinalizeTransform.replaceStoredRows() exists specifically to work around that (see §07).

02 — Foundations

Where configuration lives

One BigQuery table, parameter_store, holds every pipeline's config — as two different JSON shapes depending on what's asking.

ShapeUsed byFetched viaKey columns
Flat JSON DATA_SOURCE_DOWNLOAD BigQuerySourceConfigRepository parameter_group_name (parentId), parameter_data_source (subprocessName), parameter_name (datasourceName)
Nested JSON REPORT_PROCESSING and PIPELINE BigQueryReportRepository same three columns, keyed by reportName / reportSubprocess

PIPELINE has no config shape of its own — see §06 for why that's a deliberate, recent simplification rather than an oversight.

Token resolution — three layers, always in this order

Any query template (a BQ source query, a report transform step, a post-storage transform) resolves tokens in a fixed sequence. Getting the order wrong is the single easiest way to introduce a subtle bug here.

LayerApplies toExampleSource
1 — AliasREPORT_PROCESSING only{trades} → staged subquery or table refthe alias registry built during staging
2 — StandardBoth process types{periodStart}, {periodEnd}, {periodId}, {runDate}FrameworkOptions
3 — CustomBoth process types{exchange}, {threshold}step's own query_params_json, merged with --customParamsJson

Layer 3 has one wrinkle worth internalizing: --customParamsJson (a CLI flag, meant for Airflow DAG conf or an ad-hoc run) is merged on top of the step's stored query_params_json, and wins on any key collision. See §07 for why that's useful and what it costs.

03 — Foundations

Checkpoints & tracking tables

Every run — of either process type — leaves a durable trail in BigQuery before it starts doing anything, not after. That's what makes skip-logic, retries, and cross-process availability checks possible.

TableTracksWritten byRead by
DaReferStart/end of one DATA_SOURCE_DOWNLOAD run DataSourcePipelineFactory itself (skip logic), ReportPipelineFactory (availability + latest da_id), PipelineSequenceFactory (required/optional gate)
DaRecEvery downloaded row, paginated (≤250/page) DataSourceRecordSinkTransform; replaced by PostDownloadFinalizeTransform when a transform applies BigQueryDataSourceRecordAdapter (BnC), staged into RptStageDa
RptReferStart/end of one REPORT_PROCESSING run ReportPipelineFactory—
RptDaMapReport run → datasource mapping ReportPipelineFactoryused to clear staged data afterward
RptStageDaStaged data, batched like DaRec (one row per page) — transient stageFromDaRec()the transform chain, as an alias subquery un-nested back to individual records by stagedDataSubquery(); then deleted
RptOutputOne row per output step produced ReportPipelineFactory—
DaRefer: LOADING → COMPLETED / FAILED_BNC / FAILED_TRANSFORM / FAILED RptRefer: LOADING → COMPLETED / FAILED

Two invariants worth memorizing because several other decisions depend on them: DaRefer only ever gains rows (a re-run under --manualOverrun is always a fresh INSERT, never an overwrite), and vsn_no increments per (srce_nm, per_id) — so the history of every re-run of the same source/period stays queryable forever, even though the bulk DaRec data for superseded runs eventually gets cleaned up.

04 — Flow

DATA_SOURCE_DOWNLOAD

Fetch raw data from an API, file, or BigQuery; run per-source transforms; validate what landed; write it once, durably. This is the only flow that submits an actual Dataflow job — everything else runs in the driver JVM.

● driver JVM ● Dataflow / DirectRunner ● Beam worker
CLI invocation driver
Main.runDataSourceDownload(options) routes here based on --processType=DATA_SOURCE_DOWNLOAD.
Load config, check for a free pass
BigQuerySourceConfigRepository.fetchSourceConfigs() loads the source's flat JSON (throws immediately if the row is missing). Then isCompleted(srceNm, perId) checks DaRefer — if the latest run already shows COMPLETED, the source is skipped entirely, unless --manualOverrun or the legacy --overrideDownload bypasses the guard.
Capture what's being superseded (manualOverrun only)
fetchLatestCompletedDaId() runs before the new checkpoint is created, capturing the old da_id so its rows can be cleaned up later — but only after the new run proves itself.
createCheckpoint() — always a fresh insert
A new DaRefer row is inserted with sta_cd=LOADING and a new da_id. This never overwrites a prior row, by design.
Assemble the Beam graph — no data moves yet
Per source: resolve query tokens, fetch/derive a Schema (three fallback tiers — see the check below), route to the right connector (SourceRouter.routeFromConfig()), run the per-source transform chain (LOOKUP → GROUP_BY → SORT_BY, via SourceTransformChainAssembler), then wire DataSourceRecordSinkTransform and PostDownloadFinalizeTransform into the graph.
Submit & wait
pipeline.run(), then result.waitUntilFinish() blocks the driver JVM until Dataflow (or DirectRunner) reaches a terminal state.
Rows land, paginated worker
DataSourceRecordSinkTransform collects all rows globally, paginates at 250 rows/page, and streams one DaRec row per page. It returns a PCollection<Long> — held until every streaming insert commits — which is the input PostDownloadFinalizeTransform waits on. That's what guarantees finalization never starts before every row is actually visible in BigQuery.
Finalize, entirely inside the worker worker
No external post-pipeline step, no second DAG task. All of §checks below runs right here, then the checkpoint is updated and a failure email goes out if one is configured.

The four checks inside finalization, in order

Each one only runs if the previous one passed — a failure short-circuits the rest and leaves whatever was already stored untouched.

Check 1 — row count match (always on)

countRecords(daId) un-nests every page and counts individual rows; it must equal the row count the pipeline itself produced. No config flag turns this off.

Check 2 — min/max row bounds (optional)

From min_row_count / max_row_count in the source config. Skipped entirely if absent.

Check 3 — data_transform_query output bounds (optional)

If data_transform_query is configured, it now always runs beneath an automatically prepended WITH data AS (...) CTE that reunifies every paginated row — the operator's SQL just does FROM data. The transform's output row count is checked against data_transform_min_row_count / _max_row_count before it's allowed to replace anything already stored.

Check 4 — Balance-and-Control (BnC) sum rules (optional)

From bnc_rules_json: each rule sums a field and compares it to an expected total within tolerance. Runs against the transformed rows if check 3 applied, otherwise the raw ones.

Whatever combination fails, the checkpoint lands on the matching status — FAILED_BNC, FAILED_TRANSFORM, or plain FAILED — and, only on the happy path (COMPLETED), any superseded previous run's DaRec rows get deleted. DaRefer itself is never touched by that cleanup.

05 — Flow

REPORT_PROCESSING

Turns already-downloaded data into a report: a chain of real BigQuery jobs, file exports, and an email. Runs entirely in the driver JVM — no Beam pipeline, no Dataflow job, which is why it starts fast and is fine for small aggregated outputs.

Load config, open the checkpoint
ReportPipelineFactory.execute() calls BigQueryReportRepository.fetchReportConfig(), then BigQueryReportCheckpointAdapter.createCheckpoint() inserts a RptRefer LOADING row.
Preprocessing (optional)
Each BQ_QUERY step just runs; API_ENRICHMENT is declared in the model but not implemented yet — it logs a warning and does nothing. Worth knowing before you configure one and wonder why nothing happened.
Check datasource availability
For every required ReportDatasourceRef, DataSourceCheckpointAdapter.isCompleted() must return true against DaRefer. This is the only coupling between the two flows — a checkpoint status, not a pipeline wiring.
Stage each datasource's rows
For each ref: fetchLatestCompletedDaId() → addDaMapping() (a RptDaMap row) → stageFromDaRec(mapId, daId), which copies every DaRec page for that da_id into RptStageDa verbatim — one RptStageDa row per page, batched like DaRec itself, not one row per record. The alias registered for this datasource (stagedDataSubquery()) un-nests those pages back into individual records on every read, so a transform's SQL always sees one row per record regardless — this batching-and-unnest always runs, it's plain, unconditional SQL, not something an operator's query can opt out of, forget, or even needs to know about.
Run the transformation chain
Each step's SQL is resolved through all three token layers (§02), then BigQueryJobService.runQueryToTable() materializes it to a real table. The step's outputAlias is registered pointing at that table, so later steps can chain off it by name.
Optional: write the designated output table
If output_bq_table is set, one more query copies from output_bq_input_alias (or the last transform's alias, or the first datasource's) into it — a third, independent "final result" mechanism, separate from any per-output BQ sink below.
Route outputs, write records, clean up
ReportOutputSinkRouter exports each output to GCS, copies to a BQ table, or (not yet implemented) POSTs to an API. A RptOutput row is written per output, then clearStagedData() deletes this run's RptStageDa rows — they're intentionally transient.
Email & close out
Outputs are fetched (EmailSendUtility.FetchFileFromGcs()) and attached; the checkpoint is updated to COMPLETED — or FAILED if any phase above threw. EmailSendUtility ships no implementation in this repo — it's discovered via SPI or injected, and email is skipped with a warning (not a failure) if none is available.
Where does the report's SQL actually read from?

Never DaRec directly. RptStageDa itself is batched exactly like DaRec — one row per page, not per record — but stagedDataSubquery() un-nests those pages back into individual records the moment a transform's {alias} is substituted, so the chain's SQL always does JSON_VALUE(stage_ds_json_tx, '$.field') against a flat, one-row-per-record view — never against a raw page, and never against the still-paginated download directly.

06 — Flow

PIPELINE

Not a third system — a thin composition of the two flows above. It takes the exact same --reportName/--reportSubprocess as REPORT_PROCESSING. There is no separate pipeline config to look up.

Read the report's own datasource list
PipelineSequenceFactory calls the same BigQueryReportRepository.fetchReportConfig() REPORT_PROCESSING uses, and reads ReportConfig.datasources[] — the same List<ReportDatasourceRef>, each already carrying is_required.
Batch every declared datasource into one Dataflow job
Each ref's SourceConfig is fetched, then all of them go into a single call to DataSourcePipelineFactory.assembleForConfigs() — never one job per datasource. Anything already COMPLETED is skipped, same as standalone DATA_SOURCE_DOWNLOAD.
Submit, wait, then re-check
After waitUntilFinish(), each ref's checkpoint is re-checked. An incomplete required datasource throws PipelineException(ABORTED_REQUIRED_DATASOURCE) and the whole run stops before the report ever starts. An incomplete optional one just logs a warning.
Run the report, unchanged
ReportPipelineFactory.execute(options) runs exactly as it would under plain REPORT_PROCESSING — same object, same options, no PIPELINE-specific branch inside it.
Why this is worth understanding, not just using

This used to be a real, separate system: its own {"steps":[...]} JSON shape, its own PipelineConfig/PipelineStepConfig/DataSourceStep/ReportStep sealed model hierarchy, its own repository class. It was removed in favor of what you see above, because a report's datasources[] already said everything a pipeline needed to say — which datasources feed it, and which are mandatory. Maintaining both would have meant two places that could silently drift out of sync. See §07 for the fuller trade-off.

A detail that's easy to miss

--manualOverrun applies to the whole sequence with zero PIPELINE-specific code. The same options instance flows unchanged into both assembleForConfigs() and ReportPipelineFactory.execute(), so every declared datasource gets the same bypass-and-supersede treatment it would standalone — nothing had to be re-threaded by hand.

07 — Going deeper

Trade-offs we made, and why

Decisions that look arbitrary from the outside but weren't. Each one traded something real for something else real.

Config-as-BigQuery-rows, not code

chosen deliberately

New sources and new reports are a BigQuery row, not a deploy.

Gained
  • Zero-deploy onboarding for new sources/reports
  • One place (parameter_store) to audit all config
Cost
  • No compile-time safety on config — a typo is a runtime failure
  • Mitigated by fail-loud validation: e.g. bq_schema_json with a bad type name throws IllegalArgumentException immediately, rather than silently defaulting

DaRec pagination at 250 rows/page

write-time vs. read-time

One DaRec row holds up to 250 source rows as a JSON array, instead of one DaRec row per source row.

Gained
  • Far fewer streaming-insert calls and stored rows for large downloads
Cost
  • Every reader (row counts, BnC sums, staging, the transform CTE) must CROSS JOIN UNNEST(...) before it can see individual rows
  • Solved once, centrally, in FileHeaderLegend.dataArrayExpr() — every caller uses the same expression instead of re-deriving it

Atomic transaction for the transform's row-replace

forced by BigQuery, not chosen

Replacing a run's stored rows after data_transform_query validates runs as one BEGIN TRANSACTION ... COMMIT script (DELETE + re-paginated INSERT), not two separate jobs.

Gained
  • Never a partial state: either both statements land, or neither does
  • Safe to retry blindly on failure — a failed attempt is guaranteed to have changed nothing
Cost
  • Rows just streamed in can still be in BigQuery's DML-ineligible streaming buffer, so the whole transaction needs backoff retries (~30s total) before it's allowed to give up

data_transform_query: opt-in token → always-on CTE

recent change, this session

Used to be: unnesting only happened if the operator's SQL happened to contain the literal {data} placeholder — a silent no-op otherwise. Now: a WITH data AS (...) CTE is unconditionally prepended before every run.

Gained
  • Removes an entire footgun — forgetting the token used to mean silently querying still-paginated JSON with no error
  • Handles an operator's own WITH clause by merging CTEs instead of emitting invalid double-WITH SQL
Cost
  • The CTE always computes, even if a query somehow never references data — BigQuery optimizes this away in practice, so it's a cost mostly on paper

RptStageDa batched like DaRec — unnest moved from write to read

recent change, this session

Used to be: stageFromDaRec() un-nested every DaRec page into individual RptStageDa rows at write time — one RptStageDa row per source record. Now: it copies DaRec's pages across verbatim (one RptStageDa row per page), and stagedDataSubquery() un-nests them back into individual records on every read instead.

Gained
  • Same ~250x reduction in streaming-insert/DML volume on RptStageDa that DaRec's own pagination already gets — cheaper and faster staging
  • Zero report-facing change: {alias} still resolves to one row per record, column stage_ds_json_tx — no query_template anywhere has to change, because the unnest lives entirely inside BigQueryReportCheckpointAdapter, not in the alias resolution layer or the operator's SQL
Cost
  • Ad-hoc diagnostic queries against RptStageDa change meaning — SELECT COUNT(*) now counts pages, not records, so debugging by eye needs to remember to UNNEST first

Typed exception per process type, classified before Main ever sees it

recent change, this session

Used to be: a plain RuntimeException, three separately-shaped nested exception classes across two factories (PipelineConfigurationException defined twice, PipelineAbortedException once), and no notification path at all for REPORT_PROCESSING/PIPELINE failures — only DATA_SOURCE_DOWNLOAD had one, and only for failures caught inside PostDownloadFinalizeTransform. Now: three exceptions — DataSourceDownloadException, ReportProcessingException, PipelineException — one per process type, each carrying a Reason enum and identifying fields, classified at the point of failure by the factory that owns that process type.

Gained
  • One consistent global failure path — Main catches once, templates by type, always logs, optionally emails via the same EmailSendUtility already built for report-completion email
  • PIPELINE's composition rule is explicit and enforced by the type system: a DataSourceDownloadException/ReportProcessingException from either composed phase passes through unchanged; anything else becomes PipelineException — no accidental double-wrapping
Cost
  • Two classification techniques, not one — ReportPipelineFactory tracks a currentReason local per phase (driver-JVM, straightforward), while DataSourceDownloadException's reason for a Beam-job failure needs DataSourceFailureClassifier to walk the cause chain in beam-runner — beam-core can't instanceof-check a beam-io type like FileSourceAdapter.FileSourceException directly

--customParamsJson wins on collision

recent addition

A CLI-supplied JSON blob merges on top of a step's stored query_params_json, and beats it on any key collision.

Gained
  • Airflow DAG conf or an ad-hoc run can override one token without touching stored config
Cost
  • A silent override — an operator debugging unexpected output has to know to check the CLI args, not just the parameter_store row
  • Malformed or non-object JSON throws immediately rather than resolving to nothing, specifically so a broken override fails loudly instead of quietly changing nothing

PIPELINE simplification — reuse, don't re-model

walked back a design

The first version built a whole parallel config shape for pipelines. It was removed once it became clear a report's own datasources[]/is_required already said the same thing.

Gained
  • One less config shape, one less model hierarchy, one less repository class to keep in sync
  • --manualOverrun propagation came for free instead of needing its own logic
Cost
  • None found — this is the rare case where the simpler design was strictly better; the lesson is more about not building the bespoke shape too early in the first place

Retry policy capped at 200ms

a real limitation, by design

RetryingDoFn's delay is capped at 200ms regardless of policy (fixed or exponential).

Gained
  • Predictable worker-thread behavior — a retry never blocks a Beam worker thread for long
Cost
  • Not suitable for anything needing real back-off. The documented answer for that is a retry-topic pattern (write failures to Pub/Sub, reprocess on a schedule) — this framework doesn't build that for you

FILE sources: column letters, not header names

stability over ergonomics

CSV/Excel rows are stored keyed by Excel-style column letters (A, B, ...), with real header names carried separately as a "header legend" when a header row exists.

Gained
  • Config referencing a FILE source's fields is stable even if a header gets renamed upstream
  • Headerless files work identically — there's simply no legend
Cost
  • Every BnC rule, transform, and lookup config written against a FILE source must use column letters, not the names a human would expect
  • The legend has to be threaded through the pipeline without being mistaken for a data row — solved with a marker-wrapping convention (FileHeaderLegend) rather than a second PCollection

Dead-code cleanup: "zero callers" isn't automatically "delete it"

a judgment call, this session

A read-only sweep flagged several classes with no real callers anywhere. Some were removed; some weren't.

Removed
  • 6 unused PipelineRunConfig email/calendar getters — genuinely superseded by SourceFailureEmailConfig and --calendarName
  • BigQuerySchemaUtils.fetchRowCount()/tableExists(), an unused DataSourceRecord model, and stale docs for already-deleted JDBC code
Kept
  • RowValidationUtils, MetricsUtils, SideInputFactory, SideEffectEmailTransform — extensively documented, intentional extension points a future transform is meant to opt into directly, not leftover cruft

The one check that's a convention, not code

Serialization rules — named static DoFns, Serializable fields, transient + @Setup/@Teardown for non-serializable resources, static final TupleTags — are the one category nothing in this codebase actually enforces mechanically. Get one wrong and Beam will tell you, but only when it tries to ship a DoFn to a worker, and the resulting error is rarely obviously about serialization. Worth reading §6 of CLAUDE.md before writing a new DoFn, not after debugging one.

09 — Going deeper

Reading order & where to look

If you're about to make a change, this is the fastest path to enough context to make it safely.

  • WALKTHROUGH.md — UML diagrams and execution flows; read this first, before any code.
  • EXAMPLE.md — a full end-to-end BQ param-store example with DDL and a real run command.
  • FrameworkOptions.java (beam-core) — every CLI flag; the actual config contract.
  • Main.java (beam-runner) — the entry point; how processType routes.
  • DataSourcePipelineFactory.java — DATA_SOURCE_DOWNLOAD orchestration.
  • ReportPipelineFactory.java — REPORT_PROCESSING orchestration.
  • PipelineSequenceFactory.java — how PIPELINE composes the two above.
  • BeamTransform.java — the SPI interface; the extension contract for new transforms.

One more convention worth knowing before your first PR

This repo's CLAUDE.md treats documentation as part of every change, not an afterthought — a pre-commit hook literally blocks a commit that touches .java files without touching a README/CLAUDE.md/WALKTHROUGH.md alongside it. It's mechanical, not optional, and it's the reason the docs above stay trustworthy enough to build this guide from.
